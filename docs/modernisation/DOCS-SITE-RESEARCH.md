# User guide site: research

Research for a user guide site for Boostnote: one page per task or feature, real screenshots of the app, hosted on
GitHub Pages at `https://adrianbrowning.github.io/BoostNote/`. Checked on 2026-11-26. Every claim cites its source: a
URL for web facts, `path:line` for repo facts. "Measured" means I ran it on this machine (macOS arm64). `[INFERENCE]`
marks a claim I did not check against a source or a run.

## 1. How to structure a task-based user guide

### What Diátaxis says

- Diátaxis names four kinds of documentation: tutorials, how-to guides, reference and explanation. It says
  documentation should be organised around them (https://diataxis.fr/).
- How-to guides are "goal-oriented". They guide the user's action through a problem or towards a result
  (https://diataxis.fr/how-to-guides/).
- They "must be written from the perspective of the user, not of the machinery". A guide built on what the tool can do
  ("press Deploy") gives little value (https://diataxis.fr/how-to-guides/).
- A how-to guide is "action and only action": no digression, explanation or teaching. Link to reference or
  explanation instead (https://diataxis.fr/how-to-guides/, "Key principles").
- Its basic structure is a sequence of steps in a sensible order (https://diataxis.fr/how-to-guides/, "Describe a
  logical sequence").
- Titles should say exactly what the guide shows: "How to integrate …" is good; a bare noun is "very bad"
  (https://diataxis.fr/how-to-guides/, "Pay attention to naming").
- Use conditional imperatives: "If you want x, do y" (https://diataxis.fr/how-to-guides/, "The language of how-to
  guides").
- Reference describes the product and is "consulted", not read. It is "austere", neutral, and laid out like the
  product itself (https://diataxis.fr/reference/).
- Reference generated from the software itself stays accurate (https://diataxis.fr/reference/).

### What this means for Boostnote

- Most pages are how-to guides, one per user goal: "How to export a note as PDF", not "Export".
- One short tutorial ("Get started": open a folder as a vault, write a first note).
- A few reference pages: keyboard shortcuts, preferences, supported Markdown.
- One or two explanation pages, for example "Where your notes live" (a vault is a folder of `.md` files).
- The shortcut reference can be generated from the command table. `src/shared/commands.ts:37-95` holds every menu
  command with its label and accelerator, and the native menu is built from it (`src/shared/commands.ts:1-5`).
- Write menu paths as the app does: "File › Export" (`src/shared/commands.ts:46`).
- Some labels depend on the platform: "Reveal in Finder" / "Show in Explorer" / "Show in Folder"
  (`src/shared/commands.ts:55`), and "Settings…" on macOS but "Preferences…" elsewhere (`src/shared/commands.ts:63`).
  Pages must name both.

### Writing keyboard shortcuts

- `CmdOrCtrl` is ⌘ on macOS and Ctrl elsewhere (`src/shared/commands.ts:21`, `src/shared/commands.ts:31`).
- Some shortcuts use Ctrl on every platform: Next Tab is `Ctrl+Tab` and Previous Tab is `Ctrl+Shift+Tab`
  (`src/shared/commands.ts:73-74`). So "Ctrl" cannot always be swapped for "⌘". Generating the text from the
  accelerators avoids that mistake.
- Microsoft style: join keys with a plus sign (Ctrl+V, Alt+Ctrl+S); say "keyboard shortcut"; write "Ctrl" (not for Mac
  keyboards) and "Command" for the Mac key; spell out "Comma" and "Plus sign" in a shortcut
  (https://learn.microsoft.com/en-us/style-guide/a-z-word-list-term-collections/term-collections/keys-keyboard-shortcuts).
  This matters here because Preferences is `CmdOrCtrl+,` (`src/shared/commands.ts:64`).
- Apple's modifier symbols are Control ⌃, Option ⌥, Shift ⇧, Command ⌘ (https://support.apple.com/en-us/102650).
- HTML `<kbd>` marks keyboard input. Nested `<kbd>` elements mark the separate keys of one shortcut
  (https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/kbd).
- Proposed notation: "<kbd>⌘</kbd> <kbd>N</kbd> on macOS, <kbd>Ctrl</kbd>+<kbd>N</kbd> on Windows and Linux".

## 2. Static site generators

### VitePress

- Versions: `latest` is 1.6.4, published 2025-08-05. `next` is 2.0.0-alpha.21, published 2026-10-25
  (https://registry.npmjs.org/vitepress). The GitHub releases list 2.0.0-alpha.19 to .21 between August and October
  2026 (https://github.com/vuejs/vitepress/releases).
- vitepress.dev now documents 2.0: it installs `vitepress@next` and needs Node 22 or newer
  (https://vitepress.dev/guide/getting-started). The 1.6.4 docs live in the git tag and need Node 18 or newer
  (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/getting-started.md, line 11).
- 1.6.4 depends on `vite ^5.4.14`, `vue ^3.5.13` and `minisearch ^7.1.1`. 2.0.0-alpha.21 depends on `vite ^8.3.4`
  (https://registry.npmjs.org/vitepress, `versions[…].dependencies`).
- Measured on Node 24.19.0: a VitePress 1.6.4 site with `base: '/BoostNote/'`, local search, one Markdown page and one
  PNG built in 1.8 s. The image came out as `/BoostNote/assets/a.bxPF8Uls.png`: the base is added and the name is
  hashed.
- Measured install size (pnpm, hoisted linker): VitePress 1.6.4 is about 101 MB and 140 packages; 2.0.0-alpha.21 is
  about 92 MB and 113 packages.
- 1.6.4 brings esbuild 0.21.5, whose build script pnpm must approve (measured: `ERR_PNPM_IGNORED_BUILDS` under pnpm 12).
  The root package already allows `esbuild` in `pnpm.onlyBuiltDependencies` (`package.json:39-44`).
- Project-site base: "If you're using Github (or GitLab) Pages and deploying to `user.github.io/repo/`, then set your
  `base` to `/repo/`" (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/deploy.md, line 54). Here that is
  `base: '/BoostNote/'`. `base` must start and end with a slash, and VitePress adds it to every link that starts with
  `/` (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/reference/site-config.md, line 331).
- Local search: set `themeConfig.search.provider: 'local'`. It is a fuzzy full-text index in the browser, built on
  minisearch (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/reference/default-theme-search.md, line 7).
- Dark mode: `appearance` defaults to `true`, which follows the user's colour scheme and shows a toggle. Dark mode
  adds the `.dark` class to `<html>` (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/reference/site-config.md,
  line 490).
- Images: reference them with relative URLs. Referenced assets get hashed names, unreferenced ones are not copied, and
  images under 4 KB are inlined (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/asset-handling.md,
  lines 5, 19). VitePress does not convert or resize images, so the screenshot step must produce optimised files
  `[INFERENCE: the asset guide describes no image conversion]`.
- `img` gets `max-width: 100%; height: auto` (https://github.com/vuejs/vitepress/blob/v1.6.4/src/client/theme-default/styles/base.css,
  lines 138-142), so 2× screenshots scale down to the content column.
- Lazy images: `markdown.image.lazyLoading: true` in 1.6.4
  (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/markdown.md, line 953). 2.0 renames it to `lazyLoad`
  (https://vitepress.dev/guide/markdown, "Image Lazy Loading").
- Attributes on images: 1.6.4 includes `markdown-it-attrs` (https://github.com/vuejs/vitepress/blob/v1.6.4/src/node/markdown/markdown.ts,
  line 25). Measured: `![shot](./img/a.png){.light-only}` builds to `<img … class="light-only">`.
- Dead links fail the build unless `ignoreDeadLinks` is set
  (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/reference/site-config.md, line 440). That is a free link
  check.
- `srcExclude` excludes Markdown files from the site
  (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/reference/site-config.md, line 388). You would need it only if
  the site shared `docs/` with `docs/modernisation/`.
- Add `.vitepress/cache` and `.vitepress/dist` to `.gitignore`
  (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/getting-started.md, line 116).
- Root devDependency or separate package: VitePress can sit in a sub-folder of an existing project; the docs suggest
  `./docs` (https://vitepress.dev/guide/getting-started, "File Structure"). A pnpm workspace needs a
  `pnpm-workspace.yaml` at its root (https://pnpm.io/workspaces). This repo has none (no such file at the root). So a
  `site/package.json` with its own lockfile is a separate project, and the root `pnpm install` does not install it
  `[INFERENCE from the pnpm workspace rule]`.

### Fit with the repo's toolchain

- **Biome.** `biome check .` covers `**` except `resources`, `dist` and `build`, and it respects `.gitignore`
  (`biome.json:3-11`). Measured with the repo's Biome 2.5.15:
  - It checks `site/.vitepress/config.ts`, even inside the dot-folder.
  - It skips `site/.vitepress/dist` once that is gitignored. The root `.gitignore` already ignores `node_modules/` at
    any depth (`.gitignore:9`).
  - It formats and lints `.css`, `.ts`, `.mts`, `.vue` and `.astro` files given through `--stdin-file-path`.
  - It skips `.md` and `.yml`. `docs/modernisation/PLAN.md` and `.github/workflows/ci.yml` came back as "ignored",
    because `files.ignoreUnknown` is true (`biome.json:9`).
  - So site config and CSS follow the repo style (single quotes, no semicolons; `biome.json:40-45`). Markdown pages are
    not checked. Vue and Astro support is "Experimental" (https://biomejs.dev/internals/language-support/).
- **TypeScript 7 `tsc`.** `include` is `src`, `tests`, `scripts`, `vitest.config.ts` and `playwright.config.ts`
  (`tsconfig.json:19`). A `site/` folder is not type-checked by `pnpm typecheck` (`package.json` script `typecheck`).
  That is fine: the site's own build fails on a broken config. A screenshot spec under `tests/` is type-checked.
- **vitest** runs only `tests/**/*.test.ts` and skips `tests/e2e/**` (`vitest.config.ts:5-6`). Screenshot specs named
  `*.shot.ts` never match.
- **Playwright.** The e2e config uses `testDir: 'tests/e2e'` and `testMatch: '**/*.spec.ts'`
  (`playwright.config.ts:13-14`). A separate config in `tests/docs/` keeps screenshots out of `pnpm test:e2e`.
- **electron-builder.** `files` is an allowlist: `package.json`, `tsconfig.json`, `remix.json`, `src/**/*`,
  `resources/app.png`, minus tests (`electron-builder.yml:13-19`). So `site/` and `tests/docs/` never ship.
  electron-builder also never copies devDependencies; it copies production `node_modules` only
  (https://github.com/electron-userland/electron-builder/blob/072f05ff4b67f422e8d8d274a199e0072e9e7fe3/packages/app-builder-lib/src/options/PlatformSpecificBuildOptions.ts#L187-L189).
- **Install cost in CI.** Every CI job runs `pnpm install --frozen-lockfile` on macOS and Ubuntu, and the release job
  also runs on Windows (`.github/workflows/ci.yml:25`, `:47`, `:87`; the matrix rows above them). A root devDependency
  would add about 100 MB to each of those jobs (measured size above). A separate `site/` package adds nothing to them.

### Window size

- `win.setContentSize(width, height)` resizes the client area (the web page). It may not work on Wayland
  (https://github.com/electron/electron/blob/v45.1.0/docs/api/browser-window.md, lines 933-941).
- `electronApplication.browserWindow(page)` returns a handle to the page's `BrowserWindow`
  (`node_modules/.pnpm/playwright-core@1.64.1/node_modules/playwright-core/types/types.d.ts:19260`). So:
  `await (await app.electronApp.browserWindow(app.page)).evaluate((w) => w.setContentSize(1200, 760))`.
- The app opens at 1080×720 outer size with no saved bounds, and it has a minimum of 500×320 (`src/main/window.ts:8`,
  `:36-39`). `launchApp` writes no `windowBounds` (`tests/e2e/fixtures.ts:130-133`), so every run starts at the default.
  The committed `docs/modernisation/screenshot.png` is 1080×688 (measured), which matches the content area of that
  default window `[INFERENCE]`.
- `electron.launch` has no `viewport` or `deviceScaleFactor` option; its options are `args`, `colorScheme`, `cwd`,
  `env`, `locale`, `recordVideo` and others (`playwright-core/types/types.d.ts:24324-24560`).

### Forcing light or dark

- The renderer themes itself only through `prefers-color-scheme`:
  - `base.css` switches colours under `@media (prefers-color-scheme: dark)` (`src/app/ui/public/base.css:29`).
  - The editor and reader read `matchMedia('(prefers-color-scheme: dark)')` (`src/editor/config.ts:6-10`,
    `src/app/actions/public/workspace/reader-pane.tsx:75`).
- The app's `ui.theme` preference is `'system' | 'light' | 'dark'` and defaults to `'system'`
  (`src/main/settings.ts:13`, `:32`, `:64`). Main applies it as `nativeTheme.themeSource`
  (`src/main/preferences.ts:42-52`).
- `themeSource = 'dark'` makes `prefers-color-scheme` match dark and darkens native UI
  (https://github.com/electron/electron/blob/v45.1.0/docs/api/native-theme.md, lines 28-50).
- But Playwright's `electron.launch` emulates `prefers-color-scheme` and defaults to `'light'`
  (`playwright-core/types/types.d.ts:24358-24364`). The fixture does not pass `colorScheme`
  (`tests/e2e/fixtures.ts:178-194`). So the page renders light unless the script emulates dark. Emulation wins over
  `nativeTheme` `[INFERENCE from the documented default; not run]`.
- The existing e2e suite switches themes with `page.emulateMedia({ colorScheme })`
  (`tests/e2e/reader-diagrams.spec.ts:35`, `:41`, `:47`).
- So set both. `ui: { theme }` keeps main's native state consistent (window background `src/main/window.ts:44`; native
  menus). `page.emulateMedia({ colorScheme: theme })` decides what the screenshot shows.

Sources: https://github.com/microsoft/playwright/blob/v1.64.1/docs/src/api/params.md, lines 1346-1449, and the
installed types `playwright-core/types/types.d.ts:26829-26950`.

- `animations: 'disabled'`: finite CSS animations and transitions jump to their end; infinite ones reset to the start.
  The default for `page.screenshot` is `'allow'`.
- `caret`: `'hide'` (the default) hides the text caret.
- `scale`: `'device'` (the default) gives one image pixel per device pixel, so 2× on a Retina screen. `'css'` gives one
  pixel per CSS pixel.
- `clip: { x, y, width, height }` crops to a region. For one element, `locator.screenshot()` takes the same options
  (https://playwright.dev/docs/api/class-locator#locator-screenshot).
- `mask: Locator[]` covers elements with a box (`maskColor` sets its colour). `style` injects a stylesheet for the
  shot, for example to hide something.
- `type: 'png' | 'jpeg' | 'webp'`. For WebP, `quality: 100` (the default) is lossless and lower values are lossy
  (params.md lines 1371-1385; types.d.ts:26949).
- The release notes for 1.62 add WebP for `toHaveScreenshot` snapshots
  (https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md, "WebP screenshots").

### macOS vs Linux (xvfb)

- Playwright warns: "Browser rendering can vary based on the host OS, version, settings, hardware, power source …
  headless mode" (https://github.com/microsoft/playwright/blob/v1.64.1/docs/src/test-snapshots-js.md, line 20).
- The app uses system fonts: `system-ui, -apple-system, "Segoe UI", Roboto, …` and `ui-monospace, SFMono-Regular, …`
  (`src/app/ui/public/base.css:6-7`). macOS draws San Francisco; Linux draws whatever fallback the runner has.
  Screenshots made on the two systems will not match `[INFERENCE]`.
- CI runs e2e on Linux under `xvfb-run` (`.github/workflows/ci.yml:52-56`). Xvfb has no HiDPI, so `scale: 'device'`
  gives 1× there and 2× on a Retina Mac `[INFERENCE]`.
- Chromium's `force-device-scale-factor` switch overrides the scale factor of the UI and the page
  (https://chromium.googlesource.com/chromium/src/+/main/ui/display/display_switches.cc, line 33). Electron takes
  Chromium switches through `app.commandLine.appendSwitch` before `ready`
  (https://github.com/electron/electron/blob/v45.1.0/docs/api/command-line-switches.md, lines 5-13). `launchApp`'s only
  extra arguments are the open-file paths (`tests/e2e/fixtures.ts:134-137`), so forcing 2× on Linux would need a small
  fixture option.
- Dates in the Properties pane use `toLocaleString()` (`src/app/actions/public/workspace/properties.tsx:43`). That text
  depends on locale and time zone. `launchApp` passes `process.env` through (`tests/e2e/fixtures.ts:193`), so `TZ=UTC`
  works. `electron.launch` also has a `locale` option (types.d.ts:24324-24560), but the fixture does not set it.

### Format and size

- MDN: "WebP offers much better compression than PNG or JPEG with support for higher color depths, animated frames,
  transparency etc." (https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types).
- Measured on `docs/modernisation/screenshot.png` (1080×688), converted with sharp 0.35.5:

  | Format | Bytes | Share of PNG |
  | --- | --- | --- |
  | PNG (as captured) | 53,635 | 100% |
  | PNG, palette, level 9 | 22,606 | 42% |
  | WebP lossless | 22,882 | 43% |
  | WebP q90 | 21,186 | 40% |
  | WebP q80 | 16,934 | 32% |

- Lossless WebP costs about the same as q90 here and keeps text sharp. Playwright can write it directly
  (`type: 'webp'` at the default quality), so no extra optimisation step is needed.
- Not checked: that Electron 45's capture path writes WebP as Chrome does `[INFERENCE]`.

### Light/dark image swap in VitePress

- VitePress has a `{ light, dark }` image type, but only for theme images such as the logo
  (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/reference/default-theme-config.md, line 43). Markdown images
  have nothing built in.
- The pattern that works:
  - Dark mode adds `.dark` to `<html>` (site-config.md line 490).
  - Image attributes work (measured above).
  - Custom CSS goes in `.vitepress/theme/custom.css`, imported from `.vitepress/theme/index.ts`
    (https://github.com/vuejs/vitepress/blob/v1.6.4/docs/en/guide/extending-default-theme.md, line 21).

  ```md
  ![The editor with live preview](./screenshots/editor-light.webp){.light-only}
  ![The editor with live preview](./screenshots/editor-dark.webp){.dark-only}
  ```

  ```css
  html.dark .light-only,
  html:not(.dark) .dark-only {
    display: none;
  }
  ```

- Turn on `markdown.image.lazyLoading` so the hidden variant is not downloaded `[INFERENCE: browsers defer lazy images
  that are not rendered]`.

### What screenshots cannot show

- `page.screenshot` captures the web page only. The native menu bar, popup menus, title bar and native file dialogs
  are not in it `[INFERENCE from the API; the repo confirms Playwright cannot drive native menus,
  tests/e2e/fixtures.ts:345-347]`.
- Menus are documented as text ("File › Export › Note as PDF…") from the `COMMANDS` labels.
- In-app dialogs are web content and can be captured. Examples: Preferences (`src/app/actions/public/workspace/preferences-dialog.tsx`),
  Import (`import-dialog.tsx`), Rename from titles (`title-renames-dialog.tsx`). Open them with `clickMenu('preferences')`
  and so on.

### How screenshots are made

The docs fixture uses only existing exports from `tests/e2e/fixtures.ts`:

```ts
// tests/docs/fixtures.ts
import { rm } from 'node:fs/promises'
import * as path from 'node:path'
import { test as base, expect, type Locator } from '@playwright/test'
import { type AppHandle, launchApp, quitWithoutDialog } from '../e2e/fixtures.ts'

export type Theme = 'light' | 'dark'
const vault = path.resolve(import.meta.dirname, '../fixtures/docs-vault')
const out = path.resolve(import.meta.dirname, '../../site/screenshots')

export const test = base.extend<{ theme: Theme; app: AppHandle }>({
  theme: ['light', { option: true }],
  app: async ({ theme }, use) => {
    const app = await launchApp({}, { vaultCopyOf: vault, ui: { theme } })
    await app.page.emulateMedia({ colorScheme: theme }) // Playwright's default emulation is 'light'
    const win = await app.electronApp.browserWindow(app.page)
    await win.evaluate((w) => w.setContentSize(1200, 760))
    await app.page.waitForFunction(() => innerWidth === 1200 && innerHeight === 760)
    expect(await app.page.evaluate(() => devicePixelRatio)).toBe(2) // run on a Retina Mac
    await use(app)
    await quitWithoutDialog(app.electronApp)
    await rm(app.dir, { recursive: true, force: true })
  },
})

export async function shot(target: AppHandle['page'] | Locator, name: string, theme: Theme): Promise<void> {
  await target.screenshot({
    path: path.join(out, `${name}-${theme}.webp`),
    type: 'webp', // default quality 100 = lossless
    animations: 'disabled',
    caret: 'hide',
    scale: 'device',
  })
}
```

- Each `*.shot.ts` drives the UI the way an e2e test does, then calls `shot`. For example:
  `await app.clickMenu('preferences'); await shot(page.getByRole('dialog'), 'preferences', theme)`. Export pages can
  call `answerSaveDialog(path.join(app.dir, 'out.pdf'))` before `clickMenu('export-pdf')`.
- Projects `light` and `dark` set `use: { theme }`, so each shot runs once per theme in parallel.
- Run with `TZ=UTC` so dates render the same every time. Mask or hide anything still variable with `mask` or
  `style`.
- Run `pnpm docs:shots` by hand on a Retina Mac after UI changes or before a release. Commit the WebP files. GitHub
  shows image diffs in the PR.
- The Pages workflow never launches Electron.

### Risks

- **VitePress 1.x is old.** The last stable release is from 2025-08-05. vitepress.dev documents the 2.0 alpha, and 1.6.4
  pulls in Vite 5 and esbuild 0.21. Pin the version, read the v1 docs from the `v1.6.4` tag, and upgrade when 2.0 is
  stable.
- **Theme mismatch.** If a shot forgets `emulateMedia`, Playwright's default `'light'` emulation wins and a "dark"
  shot comes out light. The fixture above makes it one place.
- **Stale screenshots.** Nothing in CI checks the images against the current UI. Regenerate before each release.
  Optional later: a `workflow_dispatch` job on `macos-latest` that runs `docs:shots` and uploads the images as an
  artifact. Hosted macOS runners may not be HiDPI, so the 2× check would need the scale-factor switch
  `[INFERENCE]`.
- **Platform look.** Shots made on macOS show San Francisco and macOS spacing, while Windows and Linux users see their
  own system fonts (`src/app/ui/public/base.css:6-7`). Say so once on the home page.
- **Native UI is invisible.** Menus, the title bar and native dialogs cannot be captured (section 4). Describe them in
  text.
- **2× dependency.** The `devicePixelRatio` check fails on a 1× display. Making Linux shots 2× needs a fixture option
  for `--force-device-scale-factor=2` (section 4).
- **Data loader reaching outside `site/`.** Importing `../../src/shared/commands.ts` from a `.data.ts` file runs in
  Node at build time, so Vite's dev-server file restrictions should not apply `[INFERENCE]`. Check this first when
  building the shortcuts page.
  `commands.ts` imports nothing and uses only a type from `@types/node` (`src/shared/commands.ts:1-9`).
- **Biome and `.vue`.** Biome checks `.vue` files with experimental support. Keep theme customisation to `.ts` and
  `.css`. If a Vue component becomes necessary, exclude `site/.vitepress/theme/*.vue` in `biome.json`.
- **CI time.** `ci.yml` has no path filters, so docs-only PRs still run the full e2e matrix. Adding
  `paths-ignore: ['site/**']` there is an option, not part of this plan.
